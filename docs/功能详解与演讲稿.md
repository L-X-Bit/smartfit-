# A 部分 · 功能详解

## A0. 30 秒认识这个作品

| 问题 | 答案 |
| --- | --- |
| 它是什么 | 一个 AI 驱动的**个人健康 / 运动管理平台**，纯网页，电脑和手机浏览器都能用，不用装 App |
| 服务谁 | 想减脂 / 增肌 / 塑形，但「不知道怎么练、练了看不到效果、坚持不下去」的普通健身人群 |
| 怎么解决 | 用 AI 把三个环节串成闭环：**AI 给计划 → 打卡执行 → 身体与饮食数据沉淀 → AI 基于真实数据给反馈 → 计划调整** |
| 技术定位（金句） | 不是「接了个大模型」，而是**把大模型做成了可校验、可降级、可观测的业务流水线** |
| 演示数据 | 内置 demo 账号有连续 60 天的真实结构数据：62 条打卡、27 条身体记录、158 条饮食记录、13 次识图历史、4 份计划（共 248 个动作项） |

**它和「AI 套壳聊天」的区别（评委最爱问）**：AI 的输出不是一段话，而是**结构化数据落库**——计划能勾选能统计、识图结果能改份量能记账、配餐能一键采纳进今日饮食。生成过程多阶段可见，输出要过白名单校验 + 安全审核才准入库。

## A2. 数据从哪来、到哪去（一定要理解这张图）

```
【5 个数据入口】
  运动打卡 ─┐
  身体数据 ─┤
  饮食记录 ─┼─→ SQLite 数据库（server/data/smartfit.db）
  设备同步 ─┤        ↓
  计划勾选 ─┘   【服务端纯代码计算】
                    · BMR（Mifflin-St Jeor）/ TDEE / 目标热量
                    · 三大营养素目标、燃脂心率区间
                    · MET × 体重 × 时长 × 强度 → 千卡
                    · 六维健康评分（每项映射到理想区间的线性得分）
                    ↓
              【4 类 AI 输出】（模型只做决策，算术都在这之前算完了）
                    · 训练计划：多阶段 Agent 流水线
                    · 教练对话：流式 + RAG 引用 + 数据快照
                    · 拍照识图：多模态识别 + 食物库双源校验
                    · 一日配餐：模型编排 + 份量自动校正
                    ↓
              【看板】
                    数据总览 / 数据可视化 / 个人中心 AI 运行统计
```

**为什么这个顺序重要**：所有数字（BMR、目标热量、营养素、心率区间）都是**先算好再塞进提示词**的，所以模型不可能算错数——它只负责「选动作、编排餐单、写解释」。这句话在计划页、教练页、饮食页都能复述一遍。

### 2）AI 健身计划 `/plan` ★★★★★（重点一）

**这页干什么**：把「我这种情况该练什么」变成一份能勾选、能统计的结构化四周计划。

**四个区块，从上到下**：

1. **生成参数**：健身目标（减脂/增肌/塑形/保持）、每周训练天数、计划周期（周）、单次时长、训练经验、可用器械（多选）、**伤病/特殊情况（多选，AI 会回避禁忌动作）**、补充说明。右上有「大模型 · 多阶段 Agent」角标。
2. **AI 生成过程（可解释性）**：每次生成后会展开一条流水线 —— 大模型生成 → 结构校验 → 安全审核，每步带毫秒数；下面是「本次生成引用的知识库条目（RAG）」标签墙；如果有校验问题或安全审核意见，会有黄色提示条。
3. **计划正文**：计划名 + 「4 周 · 每周 4 练 · 完成度 %」；**「📋 方案说明与饮食建议」是一行折叠条，点开才显示整段方案总述和饮食建议**（默认收起，别漏讲）；下面按「第 1 周 / 第 2 周…」分 Tab，每天一张卡片（周几 + 训练重点 + 完成数），每个动作可勾选，动作下面有 💡 要点说明。
4. **历史计划**：表格（计划名 / 周期 / 动作进度 / 来源：AI 生成·规则引擎·缓存复用 / 创建时间 / 查看·删除）。

**能做什么**：
- 勾「膝关节不适」→ 生成 → 腿部动作自动变成低冲击（深蹲跳跃被剔除）
- 勾选任意动作 → **自动生成一条运动打卡**（计划与打卡打通），完成度实时上涨
- 点开折叠条看方案总述与饮食建议
- 历史计划可切回查看

**关键技术点（讲这些才显技术深度）**：
- **只让模型生成第 1 周模板，后 2~4 周由代码按渐进超负荷规则展开**。原因：一次输出四周 70+ 动作项的 JSON 会超输出上限被截断 → 解析失败 → 降级；实测那种方案 19 秒还失败，改成「模板 + 规则展开」后 7~8 秒一次通过。
- **安全规则表是纯代码写死的**，模型没有权限绕过禁忌人群限制。
- 生成耗时实测 7~8 秒（线上 8.4 秒），流程与 RAG 命中数都写在界面上。

**坑**：第一次生成会加载模型资源偏慢，**录制前先预热生成一次**；「方案说明与饮食建议」默认是收起的，想讲就点开，不想讲就跳过。

### 3）运动打卡 `/checkin` ★★★

**这页干什么**：记录一次运动，并把它换算成可信的热量。

| 能看到 | 说明 |
| --- | --- |
| 快速打卡表单 | 选择运动（可搜索动作库，动作名后面直接带 MET 值；没找到可自填名称）、时长、强度（轻松/适中/力竭）、组数/次数（力量类）、日期、感受、备注 |
| 预计消耗 | 选完运动实时显示「预计消耗 XXX kcal（按体重与 MET 估算）」 |
| 四张统计卡 | 连续打卡天数 / 本周训练天数（带目标）/ 本周时长 / 本周消耗 |
| 近 7 天运动量 | 柱线组合图（分钟 / kcal） |
| 运动类型分布 | 环形图（按时长占比） |
| 打卡日历 | 近 3 个月热力图，越深练得越多 |
| 打卡记录 | 明细表，可删除 |

**能做什么**：选动作 → 改时长 → 看预计消耗 → 完成打卡，四张卡与两张图立刻刷新。

**讲的时候强调**：热量不是拍脑袋，是 `MET × 体重 × 时长 × 强度系数` 在**服务端**算的，所以可复现、可追溯。

### 4）身体数据 `/body` ★★★

**这页干什么**：身体成分的记录与解读，是 AI 判断「你是谁、该吃多少」的输入。

- **录入表单（左）**：体重（必填）、体脂率、骨骼肌、腰围/胸围/臀围、静息心率、睡眠、记录日期。
- **四张指标卡**：当前体重、体脂率、BMI、骨骼肌，都带与上次的变化量。
- **六维健康评分（雷达图）**：BMI / 体脂 / 肌肉 / 腰围 / 心率 / 睡眠，每项映射到理想区间换算成 0~100 分。
- **体重 / 体脂趋势**：双轴折线。
- **代谢与目标**：BMR（标注 Mifflin-St Jeor 公式）、TDEE、目标热量、蛋白/碳水/脂肪目标克数 —— 右侧小字写明「用于 AI 配餐 / 训练计划」。
- **历史记录**表。

**讲的时候强调**：基础代谢、每日总消耗、目标热量、三大营养素**全部用公式算出来**，算好才进提示词 —— 从根上杜绝大模型算错数。雷达图的分数也不是拍脑袋，逻辑全在 `server/src/modules/body/routes.js` 里可查。

### 5）AI 健身教练 `/coach` ★★★★★（重点二）

**这页干什么**：一个「长在你的数据上」的健身问答教练。

**左侧对话区**：
- 顶部：「小智 · AI 健身教练」+ 状态行「已接入大模型（deepseek-chat）· RAG 知识库增强」+ 清空按钮
- 空状态欢迎语（一行说明）
- 气泡消息：**逐字流式输出**（打字机效果）；每条回答下方有「📚 引用」标签（来自本地知识库，可验证）；若走了降级会标注「本条由离线知识库（RAG 检索）生成」
- 底部常驻「推荐提问」横条（横向滚动小胶囊，点了就发问）
- 输入框 + 「Enter 发送」提示

**右侧上下文面板**：
- **注入给 AI 的数据快照**：身体、目标、趋势、健康状况、近 7 天打卡、今日饮食、计划进度，纯文本原样展示（这就是「AI 为什么答得准」的证据）
- **推荐提问**列表

**能做什么**：点任意推荐问题或自己输入 → 看流式回答 → 悬停/查看引用标签 → 对比右侧快照。

**关键技术点**：
- **SSE 流式**：首字延迟 < 1 秒，比「等十几秒一次性弹出来」体验差一个数量级。
- **RAG 检索**：知识库 172 条（动作 65 + 训练指南 25 + 食物 82），用中文分词（单字 + 二元组）+ BM25 + 结构化过滤 + MMR 去冗余，**零依赖、毫秒级命中、可解释**；不需要向量库，未来上万条时把打分函数换成向量检索即可（接口不变）。
- 回答里会出现「你近 60 天减了 3.8kg、今天蛋白 211g 达标、脂肪 50g 略偏低」这类只属于本人的数字 —— 因为快照一起发给了模型。

### 6）AI 拍照识热量 `/food-scan` ★★★★★（重点三）

**这页干什么**：拍一张饭菜照片，得到「这一餐吃了什么、多少克、多少千卡、吃法建议」。

**页面结构**：

| 区块 | 内容 |
| --- | --- |
| 顶部 | 标题 + 「多模态 AI · deepseek-chat」角标 + 今日目标 / 已摄入 / 剩余可摄入 三个数字 |
| ① 上传食物照片 | 点选/拖拽上传、手机可直接调相机；一行提示「盘边放筷子/勺子/一元硬币做参照，份量误差 ±30%」 |
| ② 识别结果 | 每种食物一行：名称 + 数据来源标签（**库内精确** / **模型估算**）+ 克数（可改，带三档快捷「份量校准」）+ 热量；下方「按总重校准」输入整盘实际重量；合计热量 + 占今日目标百分比；「AI 分析这一餐」按钮 → 给搭配结论（热量偏高/偏低/合理）；「记入饮食」选餐次 |
| ③ 识别历史 | 每条历史带原图与结果，可回看、重新记入 |
| 底部折叠条 | 「🔬 识别是怎么做的」默认收起，展开是完整技术注解（视觉识别 → 库内匹配 → 以库为准 → 冲突拦截） |
| 份量试算区 | 搜索食物库加行、填克数看热量，可「带入识别结果」，合计占今日目标比例 |

**关键技术点（这页是技术分最高的地方）**：
1. **双源交叉校验**：能匹配到食物库就用「库内精确」的每 100g 数值重算；匹配不到才用模型估算，且**标签明确区分，绝不混用**。库值与估算差 3 倍以上 → 判为误匹配，弃用库值、按估算计并标红（案例：把「面汤」错配成「意面」，300g 算出 474 kcal，真实只有 30 kcal）。
2. **泛化词剔除**：识别「碗仔面」时曾匹配到「风味酸奶」（都含「风味」），所以口味包装词（风味/原味/迷你/袋装）不作为相似依据 —— **词法相似不等于食物相似**。
3. **诚实的不确定**：照片测不出重量，所以给的是区间（如「200g，区间 150~250g，依据筷子长度推算碗口约 18cm」）+ 三档校准 + 「按总重校准」（用厨房秤称整盘 500g 输入，按比例自动分配）——**把判断权交回给人**。
4. 前端 canvas 压缩（最长边 1280px）后再上传，省流量省额度；识别结果落库（`food_scans` 表）可回溯。

**录制注意**：手机浏览器 / 电脑都能用；**微信内置浏览器拍照会失效**（页面会自动提示「在浏览器打开」），录屏请用 Chrome / Edge。

### 7）健康饮食 `/diet` ★★

**这页干什么**：一天吃了什么 + 让 AI 给出配餐方案。

- **今日热量卡**：目标 / 已摄入 / 剩余可摄入 + 蛋白质·碳水·脂肪 + 供能比环形图（蛋白 20~35% · 碳水 40~55% · 脂肪 20~30%）
- **三餐卡（早/午/晚/加餐）**：每条记录 名称 · 克数 · 千卡，可删；「添加」打开食物库搜索
- **📷 拍照识别食物热量**：本页内嵌简化版识别，右上「完整版（含识别历史）→」跳独立页
- **AI 一日配餐推荐**：点「生成配餐」→ 早中晚三餐方案 + 偏差标签 + 营养建议 → 「一键采纳到今日饮食」
- **食物营养库**：82 条食物表（热量/蛋白/脂肪/碳水/常见份量），可搜索

**关键技术点**：模型只负责「编排吃什么」，热量与营养素由代码按食物库算；模型第一次给的份量只配到 1373 kcal（差 39%），所以加了**份量自动校正**——以食物库为准等比缩放再重算，最后偏差能压到 -0.4%。**模型可以犯错，但产品不能交付错的方案。**

## A5. 12 个可讲的工程亮点（讲的时候挑 3~4 个就够）

1. 只让模型生成 1 周模板，其余由代码按渐进超负荷规则展开（避开输出上限截断）
2. 伤病禁忌是**纯代码规则表**，模型无权绕过
3. 所有算术（BMR/TDEE/热量/心率区间）在服务端算好才进提示词
4. 识图「库内精确 / 模型估算」双来源标注，绝不混用
5. 双源交叉校验：库值与估算差 3 倍判误匹配（面汤 vs 意面案例）
6. 泛化词剔除：词法相似 ≠ 食物相似（碗仔面 vs 风味酸奶案例）
7. 份量给区间 + 三档校准 + 按总重校准，承认「照片测不出重量」
8. 配餐份量自动校正，把偏差从 39% 压到 -0.4%
9. SSE 流式输出，首字 <1 秒
10. RAG 用 BM25 + 中文二元组分词，零依赖、毫秒级、可解释，还带 MMR 去冗余
11. 设备五通路：一个 API 不可用不代表功能不可用
12. 三层降级 + AI 调用日志（次数/耗时/缓存命中/降级率）——没 API Key 也能完整跑

## B1. 8 分钟主版本

### 【0:00–0:25】开场｜画面：停在数据总览

> 各位评委好，我们团队的参赛作品叫「智练 SmartFit」，一个 AI 驱动的个人健康与运动管理平台。
> 大众健身有三难：不知道怎么练、练了看不到效果、坚持不下去。市面上的产品大多只解决其中一环，而这个作品用 AI 原生思路把三环串成了闭环。

### 【0:25–1:05】数据总览｜鼠标划过四张指标卡 → 七日图 → 右下 AI 建议

> 这一屏不是演示假图，是这个账号连续六十天的记录。今天消耗、摄入、运动时长、当前体重都是实时聚合的；这张图是近七天热量收支，绿色吃进去、橙色练掉，今天有没有热量缺口一眼就看出来。
> 右下这三条建议是按我当前数据现算的——它知道我每天蛋白目标 180 克、知道我的燃脂心率是 117 到 137 之间。
> 这是整个作品的地基：**所有建议都必须站在真实数据上**。

### 【1:05–2:45】AI 健身计划（重点一）｜勾「膝关节不适」→ 生成 → 等 8 秒 → 看过程 → 看计划 → 勾一个动作

> 进入重点。我选减脂、每周四练、四周、每次四十五分钟、新手、器械徒手加哑铃。
> 关键在这一步——我勾上「膝关节不适」。很多健身 App 把伤病当装饰，我们把它当**硬约束**。
> 它在思考，大概七八秒。这七八秒里发生的事，比结果本身更值得看。
>
> 生成完了。先看上面这条流水线：大模型生成、结构校验、安全审核，每一步耗时都在，下面还列着它实际引用的知识库条目。这不是装饰，这是这个作品最核心的设计：**AI 不是黑盒，是可观测的流水线**。
>
> 再看一个工程细节：这里写着「按渐进超负荷规则由第 1 周展开至第 4 周」。我们**只让模型生成第一周的模板**，后三周由程序按规则展开。因为让模型一次输出四周、七十多个动作项的 JSON，会超输出上限被截断、解析失败、整条链路降级。实测那种方案要十九秒，最后还得退回规则引擎；改成「模板加规则展开」之后，八秒一次通过。一句话：**让模型做决策，让代码做重复劳动**。
>
> 现在看计划本身。因为勾了膝关节不适，腿部动作全是低冲击的，深蹲跳跃类被自动剔除——这不是模型自觉，我们有一张**纯代码写死的安全规则表**，模型没有权限绕过。这里有折叠的「方案说明与饮食建议」，展开还能看到整段的训练思路和饮食配套。
>
> 最后我勾选一个动作完成——注意它**自动生成了一条运动打卡**，计划和打卡是打通的。

### 【2:45–3:25】打卡 + 身体数据｜打卡页选深蹲改时长 → 完成；身体页停 3 秒划过雷达图与代谢

> 打卡不是随便填数字。选深蹲，系统自动带出 MET 值，用 MET 乘体重乘时长乘强度系数，在**服务端**算热量，所以千卡数可复现、可追溯。
> 身体数据同理：基础代谢、每日总消耗、目标热量、三大营养素目标全部用公式算出来，**算好之后才塞进提示词**，从根上杜绝大模型算错数。这张六维雷达也不是拍脑袋，每项指标都映射到理想区间换算得分。

### 【3:25–4:40】AI 教练（重点二）｜点推荐问题「膝盖有旧伤怎么安排训练」→ 流式输出 → 指引用标签 → 指右侧快照

> 这是 AI 教练。注意它**一个字一个字蹦出来**，首字延迟不到一秒。如果等十几秒一次性弹出来，用户早就关掉了。
>
> 两个细节。**第一，看这些引用标签**：它们都来自**本地知识库**，不是模型编的——动作库、训练指南、食物库一共 172 条，用中文分词加 BM25 检索，不用向量库，毫秒级命中还完全可解释。
> **第二，看右边这一块**：这是我注入给模型的数据快照，身体数据、目标、最近七天打卡、今天吃的什么、计划进度全在里面。
> 所以它答的不是通用建议，而是「你近两个月减了 3.8 公斤、今天蛋白 211 克达标、脂肪偏低」这种只属于我的答案。

### 【4:40–5:40】拍照识热量（重点三）｜拖入照片 → 等 2 秒 → 依次指来源标签 / 份量区间 / 按总重校准 / 合计

> 这是多模态能力：一张照片识别出这一餐有面条、牛肉、葱花和面汤，并估算克数。
> **重点看每个标签**：牛肉是「库内精确」，热量用食物库每 100 克的数据重算；面条面汤是「模型估算」，因为库里没有可靠条目。**两种来源明确标注，绝不混用。**
>
> 第二个设计是**双源交叉校验**：库值和估算差三倍以上，判为误匹配、弃用库值。我们踩过坑——早期把「面汤」错配成「意面」，三百克算出 474 千卡，真实只有 30 千卡。
>
> 第三个设计最实用：一张照片其实**测不出重量**。所以它给的不是假精确的数字，而是「200 克，区间 150 到 250 克，依据是筷子长度推算」。家里有厨房秤更快：称整盘 500 克输进去点「按总重校准」，按识别比例自动分配——**把判断权交回给人**。最后这一餐一键记入今日饮食，热量直接进看板。

### 【5:40–6:30】设备同步（重点四）｜划过顶部三数字 → 点「生成模拟心率」看曲线 → 滚到自动同步

> 前面数据都是人手录的，但真实用户的运动数据其实躺在手表里。这页解决「设备数据怎么进来」。
> 我们有**五条通路**：电脑和安卓 Chrome 支持网页蓝牙，能直连心率带——就是这条实时曲线；但手机上的夸克、小米浏览器，以及 iPhone 上所有浏览器**都没有实现网页蓝牙接口**，这是浏览器标准缺失，任何网页都绕不过去。
> 所以我们不把用户堵在那里：可以**手动录入**心率、**导入**手环 CSV、用脚本把 **Apple Watch 健康数据**转进来，还有**自动同步**——iPhone 快捷指令每天定时推送，安卓用 HTTP Shortcuts，电脑还有监听脚本，彻底不用导出转 CSV。
> 数据进来之后不是只展示：步数折算成步行打卡，静息心率睡眠写进身体数据，打卡日历、消耗热量、AI 判断全都跟着变。

### 【6:30–7:05】饮食 + 可视化｜配餐页点生成 → 看偏差标签；可视化切 7/30/90 天快划

> 配餐同样是「模型 + 代码」分工：模型编排吃什么，热量和营养素由代码按食物库算。注意这个偏差只有负零点四——模型第一次给的份量其实差了三成九，所以加了**份量自动校正**，以食物库为准等比缩放再重算。**模型可以犯错，但产品不能交付错的方案。**
> 可视化是七天到九十天可切换的热力图、部位均衡度、身体成分与完成度仪表盘。

### 【7:05–7:35】社区 + 工程底色 + 收尾｜社区划过信息流 → 个人中心滚到 AI 统计 → 回首页

> 社区用时间衰减的热度排序，发帖能关联打卡，把「练了」变成「被看见」。
> 最后这屏是工程底色：AI 调用次数、平均耗时、缓存命中率、降级率，**全部来自真实调用日志**，不是写死的数字。我们还做了三层降级：大模型不可用就修复重试，再不可用就退回本地规则引擎和检索式问答，**没有 API Key 也能完整运行**。
>
> 所以这个作品的核心不是「用了大模型」，而是——**把大模型变成了可校验、可降级、可观测的业务流水线**：模型只做决策，算术交给代码，知识交给检索，安全交给规则，可用性交给降级。

## B5. 评委可能追问 · 一句话回答

| 问题 | 回答 |
| --- | --- |
| 是不是套壳大模型？ | 不是。输出是结构化数据落库（能勾选能统计），生成过程多阶段可见，还要过白名单校验和安全审核才准入库。 |
| 为什么只生成一周？ | 四周 JSON 会超输出上限被截断，实测十九秒后降级；模板加规则展开八秒一次通过，这是主动的工程取舍。 |
| 不用向量库吗？ | 知识库一百七十多条，BM25 加结构化过滤加 MMR 已够用，零依赖、毫秒级、可解释；换向量只改一个打分函数。 |
| 手机连不上蓝牙怎么办？ | 这是浏览器标准缺失（iOS 全系与部分国产浏览器没实现）。所以我们做了五条通路，任何浏览器都能把数据录进来。 |
| 数据准不准？ | 算术全部在服务端用公开公式算（Mifflin-St Jeor、MET）；识图明确区分库内精确与模型估算，还有双源校验拦截误匹配。 |
| 数据能长期保留吗？ | 线上固定域名部署，数据库是 SQLite 单文件，迁 MySQL 只需改一层数据访问封装。 |
| 有多少真实用户？ | 这是参赛作品，演示账号是六十天的完整结构数据；重点在功能与技术闭环，不虚构用户量。 |
| 为什么做社区？ | 因为「坚持不下去」是真实痛点，社交激励是低成本解法。 |
| 界面文字为什么这么少？ | 长说明都做成折叠面板（方案说明、识别原理、自动同步步骤），需要时展开，不占日常使用版面。 |
| 下一步做什么？ | 接入更多设备厂商的云 API、把规则引擎换成可配置策略、把 SQLite 迁到 PostgreSQL 支持多实例。 |
