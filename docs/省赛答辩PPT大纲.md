# 省赛答辩 PPT 大纲（12 页，配套 `省赛-评委质疑应答.md` 使用）

> 设计原则：**每一页只回答一个评委问题**，数字全部来自仓库内可复跑的评测报告，不出现"大概、很多、非常准"这类词。
> 讲稿时长目标 6 分钟（12 页 × 30 秒），留 4 分钟问答。
> 数据来源：`docs/评测报告-图像识别.md`、`docs/评测报告-检索.md`；复跑：`node tools/eval-vision.mjs`、`node tools/eval-rag.mjs`。

---

## 第 1 页 · 封面

- 标题：智练 SmartFit —— AI 驱动的个人健康 / 运动管理平台
- 副标题：一个把「AI 健身教练」做成**可解释、可校验、可降级**工程流水线的作品
- 队伍：智护三角（队长 蔡鑫琪）｜赛道：AI WEB 网页开发挑战赛
- 一句话钩子（口头补充）：**"我们不比谁接的大模型多，我们比谁的 AI 能被代码和评审同时验证。"**

## 第 2 页 · 问题与洞察

- 三个痛点：不知道怎么练 / 练了看不到效果 / 坚持不下去
- 关键洞察：**健康类应用的 AI 一旦"看起来很聪明但算错了"，用户是会受伤的**
- 由此确定技术主张：算术交给代码、知识交给检索、格式交给校验、安全交给规则、可用性交给降级

## 第 3 页 · 系统架构（一页看懂）

- 前端 Vue 3.5 + Vite + Element Plus + ECharts；后端 Node 22 + Express + node:sqlite（零外部数据库）；Docker + Render 部署
- 六大模块：打卡 / AI 计划 / 身体数据 / 设备同步 / 饮食 / 社区 + 两个 AI 原生能力（教练、拍照识热量）
- 强调：单进程同源、评审 `npm install && npm run init:db && npm run dev` 三条命令可跑

## 第 4 页 · AI 流水线（本作品的核心差异化）

- 六阶段：画像 → 指标（BMR/TDEE/MET 由代码算）→ RAG 检索 → 生成 → 结构化校验与修复 → 安全审核
- 关键设计：**只让模型生成第一周模板，后三周按渐进超负荷规则展开**（实测 19 秒且会截断 → 7 秒一次通过）
- 一句话：**让模型做决策，让代码做重复劳动**

## 第 5 页 · 「待核」一：图像识别准确率（数据页）

| 指标 | 44 道菜实测 |
| --- | --- |
| 核心主食材命中率 | 48.5% |
| 食材级 类别 F1 | 43.3% |
| 非食物拒识率 | 100%（4/4） |
| 真实菜品误拒率 | 0% |
| 库内命中率 | 75.5% |
| 端到端延迟 | P50 2.89 s |

- 数据集：TheMealDB 公开 44 道菜（含 21 道中式），标注由数据库作者人工完成
- 口径：剔除 286 项"照片里看不见的调料"，只对 174 项可见主食材计分
- 讲法：**先说口径再报数字**，主动交代中式子集（类别 F1 35.7%）的差距与原因

## 第 6 页 · 准确率是怎么被改上去的（受控对比）

| 改动 | 指标变化 |
| --- | --- |
| 食物库 82 → 194 条 + 494 别名 | 库内命中率 51.4% → 75.2%（同一批 24 道菜） |
| 识图提示词加"分层拆解清单" | 严格召回 25.5% → 37.4%，核心命中 47.2% → 62.5% |
| 再补 26 条中式菜与调味 → 220 条 / 567 别名 | 库内命中率 70.0% → 75.5%，中式子集 63.3% → 75.2% |
| 识图温度固定 0 | 两次独立重跑差异 1.1pt / 2.2pt（指标可复算） |

- 讲法：**"这是同一批数据的前后对比，不是把样本换简单了"**

## 第 7 页 · 「待核」二：知识库是真检索（证据页）

- 索引是真的：`/api/rag/stats` → 65 动作 / 25 指南 / 220 食物，词表 2012，BM25 k1=1.5 b=0.75
- 打分可还原：`/api/rag/explain` → 逐词 tf/idf/贡献分；《关节不适人群的替代动作》60.56，其中「节不」+4.52、「不适」+4.35
- 对话里可见：SSE 事件 `meta → rag → delta×N → done`，`rag` 事件带 BM25 分数（现场 `curl -N` 演示）
- 质量有 golden：27 题 Recall@1 81.5% / @3 92.6% / @5 100%，MRR 0.887，单次检索 0.82 ms

## 第 8 页 · 消融实验：去掉知识库会怎样（最有说服力的一页）

同一问题「我膝盖不舒服，还想减脂，该怎么练」，`POST /api/rag/ablation` 返回两份答案：

| | 有 RAG | 无 RAG |
| --- | --- | --- |
| 引用 | 点名《关节不适人群的替代动作》《减脂热量缺口设置》 | 无引用 |
| 动作 | 只从库内选：骑行、太极、靠墙静蹲、臀桥 | 出现库里没有的动作：椭圆机、划船机、罗马尼亚硬拉 |
| 个性化 | 结合 BMI 23.7 判断"不必照搬大体重方案" | 通用建议 |

- 一句话收尾：**"如果知识库只是话术装饰，去掉它答案不会有任何变化。"**

## 第 9 页 · 严谨性：我们怎么防止 AI 出错

- 以库为准：热量一律按本地食物库重算（模型不擅算术）
- 双源交叉校验：库值与模型估算相差 >3 倍判误匹配、弃用库值并标注原因
- 安全审核 Agent：伤病 / 慢病 → 禁忌动作映射为纯规则，移除时给出自然语言理由
- 三层降级：大模型 → 修复重试 → 本地规则引擎 / 检索式问答（无 Key 无网也能完整演示）

## 第 11 页 · 创新点（技术 + 应用）

- 技术：六阶段 Agent 编排、算术外移、中文 BM25 混合检索、同构三引擎降级、双源交叉校验、全链路可观测

## 附：评委高频追问与一句话答案

| 追问 | 答案要点 |
| --- | --- |
| 47.7%/48.5% 的命中率算高吗？ | 先把口径讲清（剔除不可见调料、类别口径 vs 严格口径），再说非食物拒识 100%、误拒 0%，以及库内命中 75.5% 决定热量精度 |
| 为什么不用向量数据库？ | 知识库 220 + 65 + 25 条，BM25 + 结构化过滤已达 Recall@5 100%、0.82ms；检索层是独立类，换向量只改一处（策略模式） |
| 数据是不是挑过的？ | 数据集来自公开数据库随机抽样 + 固定 id 复用；温度固定 0，两次独立重跑差异 ≤2.2pt；报告与脚本同仓库 |
| 中餐识别为什么弱？ | 一锅多料 + 酱汁覆盖，可见食材本就少；已把库内命中率从中式 63.3% 提到 75.2% 与其他菜系持平；下一步补复合菜与真实手机样本 |
| 没有 API Key 能演示吗？ | 能，三层降级到本地规则引擎 / 检索式问答，界面诚实标注"离线知识库模式"，功能不中断 |
| 成本怎么控制？ | 语义缓存 + 按用户限流（识图 12 次/分、对话 20 次/分）+ 压缩上传（1280px/0.82）+ 图片不落盘 |
