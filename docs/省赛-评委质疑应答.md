# 省赛应答包：正面回应校赛评语的两条「待核」

> 校赛评语原文：**「拍照识热量 → RAG 教练 → AI 计划」闭环完整，多模态输入贴合健身场景，用户体验细节到位。待核：图像识别准确率、知识库是真实检索还是话术模板。**
> 两条「待核」的共同点是：**它们不是功能缺失，而是缺少可验证的证据**。省赛这一轮我们不做新功能堆砌，而是把这两件事变成**可复算的数字**。
> 本文件是答辩用的念稿 + 现场可操作步骤；跑数据用 `node tools/eval-vision.mjs` 与 `node tools/eval-rag.mjs`。

---

## 一、一句话结论（开场先说这两句）

1. **图像识别准确率**：在 44 道公开食物数据库的真实菜品（含 21 道中式菜）上，**核心主食材命中率 48.5%**、**食材类别级 F1 43.3%**、**非食物拒识 100%（4/4）**、**识别项能对上本地食物库的比例 75.5%**（中式子集 75.2%，已与其他菜系持平），端到端延迟 P50 2.89 秒。
2. **知识库是真实检索**：本地 25 条指南 / 65 个动作 / 220 种食物建成 BM25 倒排索引，27 个人工标注口语问题上 **Recall@1 81.5%、Recall@3 92.6%、Recall@5 100%、MRR 0.887**，单次检索 0.82 毫秒；并且能现场跑「关掉知识库」的对照实验，答案会明显变笼统。

> 两句话都带来源：报告在仓库里（`docs/评测报告-图像识别.md`、`docs/评测报告-检索.md`），数据和脚本同仓库，任何人可重跑得到同样数字。

## 二、质疑一：图像识别准确率 —— 我们怎么量化它

### 2.1 数据集（不是我们自己挑的好看样本）

| 项 | 说明 |
| --- | --- |
| 来源 | TheMealDB 公开食物数据库（https://www.themealdb.com/api.php），共 **44 道菜**：24 道按八类随机抽样 + 10 道中式追加 |
| 覆盖 | Chicken / Beef / Seafood / Rice / Pasta / Vegetarian / Pork / Dessert，其中**中式菜 21 道**（宫保鸡丁、麻婆豆腐、番茄炒蛋、蛋炒饭、小笼包、酸辣汤…） |
| 标准答案 | 每道菜的**食材清单与用量由数据库作者人工标注**，不是我们模型生成的 |
| 非食物集 | 4 张（3 张产品界面截图 + 1 张纯色图），专门测「会不会把截图当食物」 |
| 可复现 | `node tools/fetch-eval-dataset.mjs`（固定沿用同一批菜品 id）→ `node tools/eval-vision.mjs`；识图温度固定 0 |

> 为什么专门补中式菜：真实用户是中国大学生，中餐「一锅多料 + 酱汁遮盖」与欧美菜差别很大。
> 只报欧美菜会被问「能代表中餐吗」，所以两个子集同规则、同食物库分开报（见 2.3 分组表）。

### 2.2 指标定义（口径先说清楚，这是最容易被问的地方）

「准确率」在识图任务里不是一个数，我们给出**分层口径**：

| 口径 | 定义 | 为什么需要它 |
| --- | --- | --- |
| **严格口径** | 模型说出的名字要与标注食材名严格对上（允许互相包含 / 二元组重叠≥50%） | 最保守，作为**下界** |
| **类别口径** | 「炸鸡 / 鸡腿肉 / 鸡胸肉」视为同一食材 | 贴近用户对"认对没认对"的真实感受 |
| **核心主食材命中率** | 按标注克数取前 3 的主食材，是否被认出 | 最贴近「这盘菜是什么」 |
| **非食物拒识率** | 非食物图被判为"不含食物"的比例 | 防误报，用户最在意的体验 |
| **库内命中率** | 识别项能对上本地食物库的比例 | 决定热量用「库值精算」还是「模型估算」 |

**关键口径说明（主动交代，别等评委问）**：
标注里的「盐 / 橄榄油 / 孜然 / 香叶 / 高汤」等 **286 项调料在成菜照片里根本看不见**，我们把它们从召回分母里剔除（主食材 174 项）。
如果把它们算进去，任何看图模型的召回都会被打到 10% —— 那是**口径错误**，不是能力问题。

### 2.3 实测结果（2026-11-17，44 道菜 + 4 张非食物，识图温度 0）

| 指标 | 结果 |
| --- | --- |
| 核心主食材命中率 | **48.5%** |
| 食材级 类别 P / R / F1（宏平均） | 39.6% / 47.6% / **43.3%** |
| 食材级 严格 P / R / F1（宏平均） | 35.6% / 36.9% / 36.2% |
| 食材级 严格 P / R / F1（微平均） | 38.6% / 43.7% / 41.0% |
| **非食物拒识准确率** | **100%（4/4）** |
| 真实菜品误拒率 | **0%** |
| **识别项库内命中率** | **75.5%** |
| 份量区间自洽率（min ≤ 估 ≤ max） | **100%** |
| 份量常识范围合规率（5~800g） | **100%** |
| 端到端延迟 | P50 **2.89 s** / P95 3.91 s |

**按菜系分组（评委一定会问「中餐呢」）：**

| 子集 | 菜数 | 类别 F1 | 核心主食材命中率 | 库内命中率 |
| --- | --- | --- | --- | --- |
| 中式菜 | 21 | **35.7%** | 43.7% | **75.2%** |
| 其他菜系 | 23 | **49.8%** | 52.9% | 75.7% |

> 中餐的「类别 F1」仍偏低（35.7% vs 49.8%），但**库内命中率已经从 63.3% 提到 75.2%，与其他菜系持平**（75.7%）——
> 也就是"热量能不能用库值精算"这件事中餐不再吃亏；剩下的品类识别差距，靠补充中式复合菜与真实手机样本继续追。

**可复现性（两次数值都留档）：** 识图温度固定 0 后连续两次独立运行——类别 F1 **41.4% ↔ 42.5%**（差 1.1pt）、
核心命中率 **45.5% ↔ 47.7%**（差 2.2pt）、库内命中率 68.6% ↔ 70.0%；运行记录在 `eval/vision/results-*.json`。

> 逐菜明细、漏识清单在 `docs/评测报告-图像识别.md`，评委可现场抽查任意一条。

### 2.4 这一轮为了提准确率做了什么（受控对比，同一批 24 道菜）

| 改动 | 指标变化 | 说明 |
| --- | --- | --- |
| 食物库 **82 → 194 条**（补中式家常菜与常见食材），并新增**别名表 494 个别名**（西红柿→番茄、肯德基炸鸡→炸鸡、青豆→豌豆…） | 库内命中率 **51.4% → 75.2%**（+23.8pt） | 同一批 24 道菜前后测 |
| 再补 26 条中式成品菜与厨房调味（酸辣汤、蛋花汤、小笼包、煎蛋、酱油、豆瓣酱、香油、淀粉…）→ 食物库 **220 条 / 567 别名** | 库内命中率 **70.0% → 75.5%**；中式子集 **63.3% → 75.2%** | 同一批 44 道菜前后测 |
| 识图提示词加入「分层拆解清单」：主食 → 蛋白 → 蔬菜配菜 → 可见配料，目标 4~8 项，但**不得编造看不见的盐油香料** | 严格召回 **25.5% → 37.4%**，核心主食材命中率 **47.2% → 62.5%** | 同一批 24 道菜前后测 |
| 匹配器支持别名参与打分（正式名权重 1.0、别名 0.9），并保留「泛化词剔除 + 字符重叠率」双闸门防误配 | 回归用例 **22/22 通过**（`node tools/test-food-match.mjs`） | 负例（葱花/面汤/碗仔面）必须仍拒绝 |

> 讲这张表时必须说清：这是**同一批菜的受控对比**，不能和上面 44 道菜的全量结果相加比较（样本变难了）。

### 2.5 份量误差怎么说（不要回避）

公开数据库的用量是**整份食谱用量**（如 Chicken 500g 供 4 人），模型估的是**盘子里这一份**，两者口径天然不同，所以我们**不比 MAE**，只比量级：同量级对齐率 14.3%、中位比 0.36×（即模型系统性偏小 —— 与"单份 vs 整份"一致）。
真正用于产品的是另外两个更有意义的指标：**区间自洽率 100%**、**常识范围合规率 100%**。
更关键的是产品设计上**不依赖模型估重**：用户可以拖动克数、或直接称重后输入整餐总重一步校准，热量按本地库值重算。

### 2.6 局限（主动说，比被问出来好）

- 标注是公开数据库单一来源，未做多人复核；
- 数据集以欧美菜为主，与中式家常菜存在分布差异；
- 「主食材」清单里仍有个别被酱汁覆盖、肉眼也难辨的项，所以严格召回是**下界**；
- 下一步：加入真实手机拍摄的中式菜品样本，并公开标注流程与多人复核。

## 三、质疑二：知识库是真实检索还是话术模板 —— 五条自证

### 3.1 一条命令证明索引是真的

```
GET /api/rag/stats
→ 动作 65 条（平均文档长度 98.72 字，词表 2012）、指南 25 条、食物 220 条
→ BM25 参数 k1=1.5 / b=0.75，分词＝中文单字+二元组(bigram)
→ 高频词 DF：手(53) 力(46) 部(38) 身(37) 徒手(36) 力量(32) 居家(32)…
```
这些数字是**运行时从 `server/data/kb/*.json` 与 SQLite 真实建索引算出来的**，不是写死的常量。

### 3.2 打分可以逐词还原（不是"命中 3 条"这种黑盒）

```
POST /api/rag/explain  { "kind": "coach", "query": "我膝盖疼，怎么安排减脂训练" }
```
返回：
- **查询扩展命中了哪些规则**：膝盖→膝关节/关节不适/低冲击/替代动作；疼→疼痛/不适/替代动作/安全；减脂→热量缺口/有氧/燃脂/饮食/蛋白质
- **每条指南的 BM25 逐词贡献**：如《关节不适人群的替代动作》得分 60.56，其中 `节不`(tf=3, idf=2.85, +4.52)、`代动`(tf=3, +4.52)、`不适`(tf=5, idf=2.34, +4.35)…
- **动作检索的四段流水线**：结构化过滤（淘汰了谁、为什么）→ BM25 → 标签加权（+0.35/+0.25/−0.15 逐条标注）→ MMR 去冗余后的排序
- 最终喂给模型的上下文全文与引用列表（本次 906 字 / 6 条引用）

任何一个引用都能倒推回「哪个词 × 哪个文档 × 多少分」——**话术模板做不到这一点**。

### 3.2b 对话过程中就能看到检索（不需要任何前端配合）

教练对话的 SSE 事件序列现在是 `meta → rag → delta×N → done`：`rag` 事件在**检索完成、模型开始逐字生成之前**下发，
里面装着本轮查询扩展规则、命中的指南及 BM25 分数、选中的动作、上下文长度。现场可以直接抓流给评委看：

```bash
curl -N -X POST https://smartfit-qsyh.onrender.com/api/ai/coach \
  -H "Content-Type: application/json" -H "Authorization: Bearer <token>" \
  -d '{"question":"我膝盖疼，怎么安排减脂训练"}'
# 实测：扩展规则 4 条；指南《关节不适人群的替代动作》60.56 /《减脂热量缺口设置》45.41 /《大体重人群减脂运动建议》36.16
#       上下文 906 字；动作 骑行 / 动感单车 / 徒手深蹲 / 太极
```

这一条最直接：**如果检索是假的，压根不会有「谁得了多少分」这种东西可以下发。**

### 3.3 检索质量有 golden 标注和数字

27 个人工标注的「口语提问 → 应命中哪条指南」（例如「膝盖疼还能练腿吗」→ `gl_safety_joint`）：

| 指标 | 启用查询扩展 | 关闭查询扩展（消融） |
| --- | --- | --- |
| Recall@1 | **81.5%** | 77.8% |
| Recall@3 | **92.6%** | 92.6% |
| Recall@5 | **100%** | 100% |
| MRR | **0.887** | 0.8562 |
| 单次检索耗时 | 0.82 ms | 0.13 ms |

「关闭扩展」这一列很关键：它证明扩展规则**真的在起作用**（Recall@1 +3.7pt、MRR +0.031），而不是给回答套一层壳。

### 3.4 现场可跑的 RAG 消融实验（最强的一击）

```
POST /api/rag/ablation  { "question": "我膝盖不舒服，还想减脂，该怎么练" }
```
同一次调用返回两份答案：

| 条件 | 回答特征 |
| --- | --- |
| **有 RAG** | 「BMI 23.7 属正常范围，不必照搬大体重方案；膝盖不适要避开冲击类动作」+ 指名引用《关节不适人群的替代动作》《减脂热量缺口设置》，动作只从库里选（骑行/动感单车、太极、靠墙静蹲、臀桥） |
| **无 RAG** | 更笼统的通用建议，出现库里根本没有的动作（椭圆机、划船机、罗马尼亚硬拉），也没有引用 |

**如果知识库只是话术装饰，去掉它答案不会有任何变化。** 现场点一次就能看到差异。

### 3.5 输出随输入变（反"固定模板"）

同一个教练接口，问「膝盖疼怎么练」与问「增肌蛋白质吃多少」，命中的指南、引用条目、注入提示词的上下文（长度、条数）全部不同；扩展规则表 19 条、golden 集 27 条、别名表 567 个，全部在仓库里可查可改。
