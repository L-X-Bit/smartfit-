# 演示视频讲解稿（照读版 · 目标 7 分 30 秒）

> 用法：录参赛视频时**照着念**。左栏是「画面做什么」，右栏是「嘴上说什么」，逐字稿，不用改。
> 念稿总量约 **1700 字**，按每分钟 240 字算 ≈ 7 分 10 秒，留出生成等待和停顿正好 7 分半。
> 讲解目标：让评委记住三件事 —— **① AI 是流水线不是对话框 ② 所有数字可追溯 ③ 没网络、没硬件也能跑**。

---

```powershell
# 1. 重置演示数据（回到干净起点）
cd C:\Users\李嘉鑫\Desktop\传智杯
npm run reset:db

# 2. 启动（或双击桌面「启动智练SmartFit」）
npm run dev
```

- [ ] 浏览器开 `http://127.0.0.1:5173`，用 **demo / 123456** 登录一次
- [ ] 窗口 **1600×1000 以上**，缩放 **100%**（Ctrl+0），关掉其他标签页
- [ ] 左下角必须显示「**大模型已接入** deepseek-chat」（否则查 `server/.env` 的 `AI_API_KEY`）
- [ ] **预热**：先点一次「AI 健身计划 → 生成」，再刷新回来（首次生成要加载资源，会慢）
- [ ] 录制：`Win + G` 或 OBS，**1080p 30fps**，麦克风单独试录 10 秒
- [ ] 手机静音、关微信/QQ 弹窗；画面里**不要出现** API Key、二维码、隧道地址

## 二、逐段念稿

### 【0:00–0:25】开场

**画面**：停在「数据总览」页，鼠标不动。

**念稿**：

> 大家好，我是 XX 大学 XX 学院的 XXX，我们团队的参赛作品叫「智练 SmartFit」，一个 AI 驱动的个人健康与运动管理平台。
> 大众健身有三难：不知道怎么练、练了看不到效果、坚持不下去。市面上的产品大多只解决其中一环，而这个作品用「AI 原生」的思路把三环串成了闭环。

---

### 【0:25–1:05】数据总览

**画面**：鼠标划过四张指标卡 → 悬停「近 7 天热量收支」→ 停在右下「AI 智能建议」。

**念稿**：

> 这一屏不是假数据演示图，是这个账号连续 60 天记录的真实数据。今天消耗、饮食摄入、运动时长、当前体重都是实时聚合的；这张图是最近七天的热量收支，绿色吃进去、橙色练掉，一眼能看出今天有没有热量缺口。
> 右下这三条建议是按我当前数据现算的——它知道我每天蛋白目标 180 克、知道我的燃脂心率区间是 117 到 137。
> 这是整个作品的地基：**所有建议都必须站在真实数据上**。

---

### 【1:05–2:45】AI 健身计划 —— 重点一

**画面**：目标「减脂」、每周 4 天、4 周、45 分钟、新手、器械「徒手+哑铃」，**勾选「膝关节不适」**（一定要勾），点「生成我的专属计划」，等约 7 秒。

**念稿（点之前）**：

> 现在进入重点。我输入减脂、每周四练、四周、每次四十五分钟、新手、器械是徒手加哑铃。
> 关键在这里——我勾上了「膝关节不适」。很多健身 App 把伤病当装饰，我们把它当**硬约束**。

**念稿（等待时别冷场）**：

> 它在思考，大概七秒。这七秒里发生的事，比结果本身更值得看。

**念稿（生成完成后，语速放慢）**：

> 生成完了。先看上面这条——大模型生成约 7 秒、结构校验、安全审核，还列出了它实际引用的知识库条目。这不是装饰，是我们最核心的设计：**AI 不是黑盒，是可观测的流水线**。

> 再看一个工程细节：这里写着「按渐进超负荷规则由第 1 周展开至 4 周」——我们**只让模型生成第一周模板**，后三周由程序按规则展开。
> 因为让模型一次输出四周、七十多个动作项的 JSON，会超输出上限被截断、解析失败、整条链路降级。我们实测过：那种方案 19 秒，最后还是退回规则引擎；改成「模板 + 规则展开」后 7 秒一次通过。
> 一句话：**让模型做决策，让代码做重复劳动。**

> 现在看计划本身。因为勾了膝关节不适，腿部动作全是低冲击的，深蹲跳跃类被自动剔除——这不是模型自觉，我们有一张**纯代码写死的安全规则表**，模型没有权限绕过。
> 最后我勾选一个动作完成——注意它**自动生成了一条运动打卡**，计划和打卡是打通的。

---

### 【2:45–3:25】运动打卡 + 身体数据

**画面**：切「运动打卡」→ 选「徒手深蹲」→ 时长改 30 → 看“预计消耗” → 完成打卡；再切「身体数据」停 3 秒，划过雷达图与代谢指标。

**念稿**：

> 打卡不是随便填数字。选深蹲，系统自动带出 MET 值，用 MET 乘体重乘时长乘强度系数在**服务端**算热量，所以千卡数可复现、可追溯。
> 身体数据同理：基础代谢、每日总消耗、目标热量、三大营养素目标全部用公式算出来，**算好才塞进提示词**，从根上杜绝大模型算错数。

---

### 【3:25–4:40】AI 健身教练 —— 重点二

**画面**：切「AI 健身教练」→ 点推荐问题「我想减脂，但膝盖有旧伤，怎么安排训练？」→ 流式输出。

**念稿（输出中）**：

> 这是 AI 教练。注意它**一个字一个字蹦出来**，首字延迟不到一秒。如果等十几秒一次性弹出来，用户早就关掉了。

**念稿（正文出来后，鼠标停来源标签，再移右侧数据快照）**：

> 两个细节。**第一，看这些标签**：它引用「关节不适人群的替代动作」「减脂热量缺口设置」等条目，都来自**本地知识库**，不是模型编的，点开能验证。我们用 BM25 加查询扩展，不需要向量库，一百多条知识毫秒级命中，还完全可解释。
> **第二，看右边这一块**：这是我注入给模型的数据快照——身体数据、目标、最近七天打卡、今天吃的什么、计划进度全在里面。
> 所以它答的不是通用建议，而是「你这 60 天减了 3.3 公斤、体脂降了 3.4 个点、今天蛋白还差 53 克」这种只属于我的答案。

---

### 【4:40–5:40】AI 拍照识热量 —— 重点三

**画面**：切「AI 拍照识热量」→ 拖一张饭菜照片 → 等约 2 秒 → 鼠标依次停：来源标签 / 份量依据 / 份量校准位 / 合计热量。

**念稿**：

> 这是多模态：一张照片识别出这一餐有面条、牛肉块、葱花和面汤，并估算克数。
> **重点看每个标签**：牛肉是「库内精确」，热量用库里每 100 克数据重算；面条面汤是「模型估算」，因为库里没有可靠条目。**两种来源明确标注，绝不混用。**

> 第二个设计是**双源交叉校验**：库值和估算差三倍以上，判为误匹配、弃用库值。我们踩过坑——早期把「面汤」错配成「意面」，300 克算出 474 千卡，真实只有 30 千卡。
> 还有个更隐蔽的：识别「碗仔面」时检索匹配到「风味酸奶」，因为都带「风味」两字。所以匹配层加了**泛化词剔除**——词法相似不等于食物相似。

> 第三个设计最实用：一张照片其实**测不出重量**。所以它给的不是假精确的数字，而是「200 克，区间 150 到 250 克，依据是筷子长度推算出碗口约 18 厘米」。
> 家里有厨房秤更快：称整盘 500 克输进去点「按总重校准」，按识别比例自动分配——**把判断权交回给人**。

---

### 【5:40–6:30】设备同步 —— 五条通路

**画面**：切「设备同步」→ 划过顶部指标卡 → 点「无设备？生成一段模拟心率」看曲线跳动 → 滚到「自动同步 / 同步令牌」。

**念稿**：

> 前面数据都是人手录的，但真实用户的运动数据其实躺在手表里。这页解决「设备数据怎么进来」。
> 我们做了**五条通路**：电脑和安卓 Chrome 支持网页蓝牙，能直连心率带——就是这条实时曲线；但手机上的夸克、小米浏览器，以及 iPhone 上所有浏览器**都没有实现网页蓝牙接口**，这是浏览器标准缺失，任何网页都绕不过去。
> 所以不把用户堵在那里：可以**手动录入**心率、**导入**手环 CSV、用脚本把 **Apple Watch 健康数据**转进来，还有**自动同步**——iPhone 快捷指令每天定时推送，安卓用 HTTP Shortcuts，电脑还有监听脚本，彻底不用导出转 CSV。
> 数据进来后不是只展示：步数折算成步行打卡，静息心率睡眠写进身体数据，打卡日历、消耗热量、AI 判断全都跟着变。

---

### 【6:30–7:05】健康饮食 + 数据可视化

**画面**：切「健康饮食」→ 点「AI 一日配餐」→ 等约 4 秒 → 停在「与目标偏差」标签 → 切「数据可视化」快速划过六张图。

**念稿**：

> 配餐同样是「模型 + 代码」分工：模型编排吃什么，热量和营养素由代码按食物库算。
> 注意这个偏差 -0.4%——模型第一次给的份量其实只配到 1373 千卡、差 39%，所以加了**份量自动校正**：以食物库为准按比例缩放再重算。**模型可以犯错，但产品不能交付错的方案。**
> 可视化是七天到九十天可切的热力图、部位均衡度、身体成分和完成度仪表盘。

---

### 【7:05–7:35】社区 + 工程底色 + 收尾

**画面**：切「运动社区」划过信息流 → 切「个人中心」滚到「AI 运行统计」→ 回首页停在左下「大模型已接入」。

**念稿**：

> 社区用时间衰减的热度排序，发帖能关联打卡，把「练了」变成「被看见」。
> 最后这屏是工程底色：AI 调用次数、平均耗时、缓存命中率、降级率，**全部来自真实调用日志**，不是写死的数字。我们还做了三层降级：大模型不可用就修复重试，再不可用退回本地规则引擎与检索式问答，**没有 API Key 也能完整运行**。

> 所以这个作品的核心不是「用了大模型」，而是——**把大模型变成了可校验、可降级、可观测的业务流水线**：模型只做决策，算术交给代码，知识交给检索，安全交给规则，可用性交给降级。
> 谢谢各位评委。

> 社区用时间衰减的热度排序，发帖能关联打卡，把「练了」变成「被看见」。最后这屏是工程底色：AI 调用次数、平均耗时、缓存命中率、降级率，全部来自真实调用日志，不是写死的数字。我们还做了三层降级：大模型不可用就修复重试，再不可用退回本地规则引擎与检索式问答，没有 API Key 也能完整运行。所以这个作品的核心不是「用了大模型」，而是把大模型变成了可校验、可降级、可观测的业务流水线：模型只做决策，算术交给代码，知识交给检索，安全交给规则，可用性交给降级。谢谢各位评委。

## 四、录制小技巧

| 问题 | 处理 |
| --- | --- |
| 某段卡壳 | **不要停录**，停 2 秒接着往下说，后期剪掉 |
| 生成/识别比预期慢 | 别说"怎么这么慢"，改说「它在思考，这几秒它做的是……」，把等待变成讲解点 |
| AI 突然超时 | 别现场改配置，直接说「这次网络波动，三层降级会退回规则引擎，功能不中断」——本身就是亮点 |
| 时长超 8 分钟 | 优先删：可视化（-35 秒）、饮食（-35 秒）、社区（-30 秒）；**四个重点不能删**（计划/教练/识图/设备） |
| 数据太好或太差 | 都用真数据，别 P 图，评委可能对着屏幕核对 |

## 五、可选：把「问答」也录进去（+60 秒）

| 可能的问题 | 一句话回答 |
| --- | --- |
| 大模型是不是套壳？ | 不是。计划是结构化 JSON 落库、能勾选能统计；生成过程六阶段可见；输出要过白名单校验与安全审核才能入库。 |
| 为什么只生成一周？ | 四周 JSON 超输出上限会被截断，实测 19 秒后降级；模板加规则展开后 7 秒一次通过，这是主动的工程取舍。 |
| 不用向量库吗？ | 知识库 166 条，BM25 加结构化过滤已够用，零依赖、毫秒级、可解释；检索层是独立类，换向量只改一处。 |
| 手机连不上蓝牙怎么办？ | 这是浏览器标准缺失（iOS 全系与部分国产浏览器没实现）。所以我们做了五条通路，任何浏览器都能把数据录进来。 |
| 数据能长期用吗？ | 线上部署在云平台、域名固定；数据库是 SQLite 单文件，迁 MySQL 只需改一层数据访问封装。 |

提词器纯念稿实测 **2225 字**：按每分钟 280 字（带演示的自然语速）≈ 8 分，加上生成等待约 15 秒，
