## 🔴 高｜AI 拍照识热量：JPEG / 纯色图上传确定性 500，偶发 >60s 挂起

**根因**（三处叠加）
1. 图片校验只看体积：`buffer.length < 8KB` 直接判死。一张纯色 PNG 压缩后只有一两百字节，
   明明合法却被拒；
2. 上限前后不一致：`express.json` 限 10MB、zod 限 12MB、业务层限 6MB。手机原图（>6MB）触发业务层异常，
   而 `express` 的 413 又没被识别，都被打成「服务器内部错误」；
3. `AiError` 不是 `BizError`，也不带 `httpStatus`，于是错误中间件一律走「未知异常 → 500」，
   真正的失败原因（超时 / 上游拒图 / 图片过大）全被吞掉；`visionChat` 沿用文本的 60s 超时且无重试，
   表现就是「偶发 >60s 挂起」。

**改法**
- `server/src/ai/foodVision.js`：新增 `decodeImagePayload()`，**按文件头魔数**判断真实格式
  （PNG `89504E47` / JPEG `FFD8FF` / WebP `RIFF....WEBP`），兼容 dataURL、大写 MIME、裸 base64；
  体积只拦「空文件/明显损坏」（默认 64 字节下限），纯色小图交给模型判断是不是食物；
  格式不对返回 **415**，超限返回 **413**，都带具体 MB 数。
- `server/src/config/index.js`：新增 `uploads.{maxBodyBytes,maxImageBytes,minImageBytes}` 与
  `ai.visionTimeoutMs`（默认 30s），三个上限统一由一处决定。
- `server/src/ai/provider.js`：`requestOnce` 支持按场景覆盖超时；`visionChat` 用 **15s 预算**
  （`AI_VISION_TIMEOUT_MS`）+ 剩余预算足够时才重试 1 次；上游英文报错翻译成中文结论。
- **优雅降级**（按报告第六节的修复建议实现）：上游超时 / 网络抖动 / 上游拒图，一律返回
  `code: 0` + `{ notFood: true, degraded: true, reason }`，前端照常渲染「没识别到食物 + 原因 + 换一张」，
  用户不会看到 500，也不会只看到一句「服务器内部错误」。
- `server/src/modules/foodscan/routes.js`：再加**两层兜底**
  1. `Promise.race` 硬超时（预算 + 0.5s），保证「任意输入 15s 内必返回」即使网络栈异常也成立；
  2. **整条链路 try/catch**：除「图片过大 / 不是图片 / 未配置视觉模型」这类用户可自行处理的 4xx 外，
     任何未预期异常都降级成「没识别到食物 + 原因 + 重试/手动记录」，**绝不向页面抛 500**
     （这就是把 `ai/vision-food` 的兜底思路搬过来，并补上了可读原因）。
- 图片格式新增 **GIF** 支持，并对 iPhone 的 **HEIC** 单独给「编辑 → 存储为 JPG」的操作指引。
- `server/src/middleware/error.js`：`AiError` 按「能不能重试」翻译成 502 / 503 / 504 / 429。

**回归脚本**：新增 `tools/test-foodscan.mjs`（纯 Node，无依赖），一条命令即可对任意环境复测：

```bash
node tools/test-foodscan.mjs                                          # 本地
APP_URL=https://smartfit-qsyh.onrender.com node tools/test-foodscan.mjs  # 线上（部署后复测）
```

它会跑「纯色 PNG / 渐变 PNG / 噪声大图 / 1×1 GIF / 字节损坏 JPEG / 真实截图」六种输入，
判定「不得 500、必须 15s 内返回、该降级的有降级标记」。当前本地 **6/6 通过**；
线上旧构建 **2/6**（纯色 500、损坏 JPEG 500、GIF 400）。

**验证**（均实测通过）
| 用例 | 修复前 | 修复后 |
|---|---|---|
| 纯色 PNG（136 字节） | 500 | **200**（881ms，模型判定「非食物」） |
| 真实 JPEG（1280×960，38KB） | 500 | **200**（869ms，判定「非食物」） |
| 13MB 手机原图 | 500 | **413**「图片过大（13.0MB，上限 12MB），请压缩后再试」 |
| 损坏的 JPEG 字节流 | 500 | **502**「这张图片无法被识别（文件可能损坏…）」 |
| 根本不是图片的内容 | 500 | **415**「不是有效的图片文件…HEIC 请先转 JPG」 |

## 🟠 中｜错误处理太糙：除 400 外全部裸 500，无细分、无 requestId

**改法**
- `server/src/middleware/common.js`：新增 `requestId` 中间件，每请求一个短 id，写进
  `res.locals`、响应头 `X-Request-Id`，并打印在请求日志里。
- `server/src/middleware/error.js`：重写分类逻辑，响应体统一为
  `{ code, message, requestId, data, ... }`：

  | 状态码 | 场景 | 用户看到什么 |
  |---|---|---|
  | 400 | Zod 校验 / 请求体不是合法 JSON | 指出具体字段 |
  | 401 / 404 | 未登录、资源不存在 | 原业务提示 |
  | 413 | 请求体或图片过大 | 「图片过大（x MB，上限 y MB）」 |
  | 415 | 不是有效图片 | 「仅支持 JPG / PNG / WebP」 |
  | 429 | AI 限流 | 「请稍后再试」 |
  | 502 | AI 上游失败 | 中文结论 + `retryable` |
  | 503 | SQLite 写锁竞争 | 「请 2 秒后重试」+ `Retry-After` |
  | 504 | AI 超时 | 「识别超时（30s 未返回），请换一张更小的照片」 |
  | 500 | 真未知异常 | 「请把请求号 xxx 反馈给开发者」（堆栈只进日志） |

- 前端 `web/src/api/index.js` 把 `requestId` 拼进提示，用户报障时能直接给出请求号。

**验证**：`GET /api/definitely-not-exist` → `404` + `requestId`；各错误响应体均含 `requestId`。

## 🟠 中｜「今日」数据日期钉死，中国时区 / 种子数据错位

**根因**：两个问题叠加
1. 云平台进程时区是 UTC，`new Date().getHours()` / SQLite 的 `datetime('now','localtime')` 都按 UTC 走，
   中国时间 00:00~08:00 之间「今天」会少一天（报告里首页显示 `2026-10-31`、本地已是 `2026-11-01`）；
2. 种子数据在部署那一刻写死，之后不会随日期滚动。

**改法**
- `server/src/config/index.js`：启动最早期设置 `process.env.TZ = APP_TZ`（默认 `Asia/Shanghai`），
  Node 与 SQLite 的 `localtime` 完全一致。
- `server/src/db/index.js`：`today()` / `nowStr()` 改为按 `config.timezone` 用 `Intl.DateTimeFormat`
  计算（与服务器时区无关）；`shiftDate` 改为纯 UTC 日历运算；新增 `daysBetween`。
- `server/src/db/demoRefresh.js`（新增）：**启动时演示数据保鲜**——取演示账号最近一条业务日期，
  若早于今天就把 `body_records / workout_logs / diet_logs / plans / device_syncs.payload` 等
  整体平移 N 天（含 `created_at`），只处理种子账号（demo/lily/coach/runner），
  今天有真实数据时 delta=0 不做任何事，偏差超过 365 天视为异常直接跳过。开关：`DEMO_AUTO_SHIFT`。

**验证**：`GET /api/dashboard/overview` 返回 `date: "2026-11-01"`，与 `Asia/Shanghai` 一致；
把演示数据整体回拨 5 天后重启，日志输出
`[演示数据] 已整体平移 5 天：2026-10-27 → 2026-11-01`。

## 🟠 中｜Render 免费版冷启动 20~30s，首屏卡「Application loading」

**根因**：`index.html` 只有一个空的 `<div id="app">`，实例冷启动那 20~30 秒里用户看到的是白屏；
首批接口也没有重试，冷启动期间的超时会被当成「服务坏了」。

**改法**
- `web/index.html`：加**纯 CSS 首屏插屏**（品牌 + 进度条 + 「首次访问需要唤醒服务 20~30 秒，请勿关闭页面」），
  不写内联 `<script>`，不违反 CSP。
- `web/src/main.js`：挂载完成后淡出并移除插屏；新增 `keepWarm()`，页面可见时每 10 分钟
  轻量 ping `/api/health`，演示期间实例不会中途睡回去。
- `web/src/api/index.js`：GET 请求遇到「无响应 / 502 / 503 / 504」自动重试 2 次（2s + 4s），
  首次重试弹出「服务正在唤醒（免费实例冷启动约 20~30 秒）」，超时上限 45s；
  连不上时的提示也改成可照做的中文。
- `server/src/index.js`：显式 `listen(config.port, '0.0.0.0')`（不传 host 时 Node 绑到 `::`，
  部分容器环境 IPv4 连不上，健康检查会一直失败），并对 `EADDRINUSE` 给出可读提示。

**验证**：把网络限速到 30KB/s 打开页面，1.2s 时截图为插屏（不再是白屏）；
应用挂载后插屏被移除。真实浏览器登录回归：无控制台错误、无 4xx/5xx。

## 🟢 低｜前端 token 存 localStorage（XSS 风险）；演示密码 123456

**改法**
- **登录态改成 HttpOnly Cookie**：`POST /api/auth/login|register` 通过 `Set-Cookie: sft_token=...;
  Path=/; HttpOnly; SameSite=Lax[; Secure]` 下发（`server/src/modules/auth/routes.js`）；
  新增 `POST /api/auth/logout` 清 Cookie。
- `server/src/middleware/auth.js`：Cookie 优先、`Authorization: Bearer` 保留（命令行 / 自动化测试 / 第三方调用不受影响）。
- 前端 `web/src/api/index.js`：`withCredentials: true`；`tokenStore.set()` **不再把 JWT 写进 localStorage**，
  只记一个 `smartfit_auth=1` 的登录标记；路由守卫改用标记判断。老客户端 localStorage 里的 token 仍可用（向后兼容）。
- `web/src/app.js` 安全响应头：`Content-Security-Policy`（`script-src 'self'`、`connect-src 'self'` 等）、
  `X-Content-Type-Options: nosniff`、`Referrer-Policy`、`X-Frame-Options`。即使出现 XSS，外部脚本也执行不了、
  token 也读不到（HttpOnly）。
- 演示账号 `demo / 123456` 是评审要求保留的公开入口，未改动；如正式上线建议在 `users` 表加
  `is_demo` 标记并限制其只能读。
- **注册 / 登录加固**（对应报告「注册接口可随意注册，正式环境需加限流 / 验证码 / 强制改密」）：
  · 注册接口限流 **5 次 / 小时 / IP**，密码强度要求「≥8 位且含字母与数字」（仅注册校验，老账号登录不受影响）；
  · 登录接口限流 20 次 / 分钟，并做**失败锁定**：同 IP + 账号 10 分钟内失败 5 次 → 锁 5 分钟（429 + 剩余秒数），
    锁定只作用于该账号，演示账号不会被旁人试错牵连；
  · 验证码需要额外服务（短信/图形码），比赛环境改用「限流 + 锁定 + 强度校验」，上线前若要做公开注册建议再补图形验证码。

**验证**：真实浏览器登录后
`localStorage.smartfit_token = null`（不再明文存凭证）、`document.cookie` 中看不到 `sft_token`（HttpOnly 生效）、
刷新后仍保持登录（走 Cookie）；响应头含 CSP 与 `nosniff`；
弱密码注册被拒（「密码至少 8 位」），连续 6 次错误密码触发 429 锁定，演示账号仍可正常登录。

## 接口兼容性加固（报告「红标澄清」里暴露的字段差异）

报告里的红标多数是探测写法不同（如用 `GET` 探 `POST` 接口），代码没坏；但为了降低外部联调成本，补了几处别名兼容：

| 场景 | 之前 | 现在 |
|---|---|---|
| 计划生成目标 | 只认 `lose / gain / keep / shape`，传 `maintain` 报 400 | 支持 `maintain / maintenance / fat_loss / muscle_gain / 减脂 / 增肌 / 保持 / 塑形` 等别名，报错信息里列出可选值 |
| AI 教练提问 | 只认 `question` | `question` 或 `message`（OpenAI 风格）都认 |
| 运动打卡 | 只认 `exerciseName` | `exerciseName / exercise / name` 都认；`duration` 也映射到 `durationMin` |
| `POST /api/ai/vision-food` 偶发 502 | 直接把 502 抛给页面 | 上游抖动时**降级返回**空结果 + 可读原因（`degraded: true`），并保留内部一次重试 |
