### 录制注意事项
- 分辨率 ≥ 1080p，浏览器缩放 100%，窗口 1600×1000 以上（页面按此宽度设计）。
- 录之前执行 `npm run reset:db` 重置演示数据，保证数据整洁。
- 提前把 `.env` 里的 `AI_API_KEY` 配好：**有 Key** 的版本更有说服力（展示真实大模型与秒级生成）；
  另可保留一段**无 Key 降级**的对比镜头，反而能体现工程完备性。

## 二、值得展开讲解的代码位置（提词卡）

| 讲解主题 | 文件 | 一句话讲法 |
| --- | --- | --- |
| **AI 六阶段编排** | `server/src/ai/planAgent.js` | 头部注释就是整条流水线的 ASCII 图，从「画像」到「安全审核」六步，任一步失败进降级。「模型只做编排，算术交给代码」。 |
| **为什么模型算不对热量** | `server/src/utils/health.js` | BMR 用 Mifflin-St Jeor、TDEE 乘活动系数、热量用 MET 公式——全部确定性代码，算好写进提示词并声明"不得修改"。 |
| **RAG 怎么做的** | `server/src/ai/rag.js` | 中文没有空格，用「单字 + 二元组」自己实现 BM25；再叠加结构化过滤（器械/难度/伤病）、标签加权、MMR 去冗余。文件头注释写了"为什么不用向量库"。 |
| **防幻觉的校验** | `server/src/ai/validators.js` | 剥代码块 → 截 {} → 修尾逗号 → 字段归一化 → **动作白名单比对**（编造的 exerciseId 直接丢弃）→ 数值夹取 → 周次补全。 |
| **安全审核** | `server/src/ai/profile.js`（`CONDITION_RULES`） | 伤病 → 禁忌动作是一张纯规则表，审核不依赖模型自觉；审核结论会以中文反馈到界面上（"已移除「跳绳」：不适合膝关节不适人群"）。 |
| **降级怎么做** | `server/src/ai/fallback.js` | 规则引擎产出**结构完全相同**的计划对象，所以前端一行代码都不用改。 |
| **流式输出** | `server/src/modules/ai/routes.js` + `web/src/api/index.js` | 后端 `text/event-stream` 推 `meta → delta×N → done`；前端用 fetch + ReadableStream 手解析 SSE（因为要带 JWT，EventSource 不支持自定义 Header）。 |
| **语义缓存** | `server/src/ai/cache.js` | 画像数值量化后生成指纹做 key，LRU + 30 分钟 TTL；重复生成毫秒级。 |
| **可观测性** | `server/src/ai/observability.js` | 每次调用落一条 `ai_call_logs`，个人中心的统计面板直接读它——优化用数据说话。 |
| **热量为什么可信** | `server/src/modules/checkin/routes.js` | 前端只传时长和强度，热量在服务端算，并回传 `{calories, met, weightUsed}` 让用户看到依据。 |
| **计划→打卡闭环** | `server/src/modules/plan/routes.js`（`PATCH /items/:id`） | 勾选动作时可带 `autoCheckin`，自动按「组数×次数×3 秒」估时长并生成打卡，打卡再能分享到社区。 |
| **社区热度分** | `server/src/modules/community/routes.js`（`calcHotScore`） | 点赞×3 + 评论×5 + 基础 6，再乘时间衰减（每 24h 衰减 10%），新旧内容都有机会。 |
| **零依赖数据库** | `server/src/db/index.js` + `schema.sql` | 用 Node 内置 `node:sqlite`，评审克隆后不用装任何数据库；14 张表的 DDL 全带中文注释。 |

## 三、预设问答（答辩备用）

<details>
<summary><b>Q1：这里的 AI 是不是只是套了个聊天框？</b></summary>

不是。三个证据：
1. AI 生成的计划是**结构化 JSON 并落库**的，能勾选、能统计进度、能生成打卡；
2. 生成过程有**六阶段流水线**，每阶段耗时与结论在前端可见，还展示 RAG 引用；
3. 模型输出必须通过**白名单校验 + 安全审核**才能入库，不通过会自动修复重试或降级。
</details>

<details>
<summary><b>Q2：大模型会不会瞎编动作？</b></summary>

三层防御：① 提示词里给出动作白名单并声明禁止编造；② 校验阶段把 exerciseId 与数据库比对，失配即丢弃（并计入修复统计）；③ 最终还要过安全审核。
另外 MET、热量、营养素这些数值根本不进模型的"计算范围"，由代码算好后注入。
</details>

<details>
<summary><b>Q3：没有 API Key 怎么演示？</b></summary>

设计了三层降级：大模型 → 修复重试 → 本地规则引擎/检索式问答。没有 Key 时计划由规则引擎生成（分化模板 + 动作库筛选 + 渐进超负荷 + 文案模板），教练用 BM25 检索知识库后按模板作答，界面会诚实标注"离线知识库模式"。
</details>

<details>
<summary><b>Q4：为什么不用向量数据库做 RAG？</b></summary>

知识库只有 166 条（动作 65 + 食物 76 + 指南 25），BM25 + 结构化过滤已足够，且零依赖、毫秒级、可解释（能看命中词）。
代码里 `BM25Index` 是独立类，未来接 embedding 只需替换 `score()`，上层接口不变。
</details>

<details>
<summary><b>Q5：数据存在哪？会不会丢？</b></summary>

SQLite 单文件（`server/data/smartfit.db`），WAL 模式。数据访问全部收敛在 `db/index.js` 的 `get/all/run/tx` 四个方法，要迁 MySQL 只改这一层。
`npm run reset:db` 可随时重置演示数据。
</details>

<details>
<summary><b>Q6：为什么选 Vue 而不是 React？技术深度在哪？</b></summary>

选 Vue 3 是因为 Composition API 让"按功能聚合"更自然，团队开发效率高；技术深度不在框架本身，而在：
自实现中文 BM25、JSON 结构化输出校验器、多阶段 Agent 编排、SSE 手写解析、语义缓存与可观测性、同构降级设计。
</details>
